## 1. The Three Pillars of Observability

The Agentic Business OS implements the three core pillars of modern system observability: **Metrics**, **Structured Logs**, and **Distributed Traces**, unified by common correlation tags (`tenantId`, `correlationId`, `workflowId`).

```
┌─────────────────────────────────────────────────────────────────────────────┐
│                           UNIFIED TELEMETRY COLLECTOR                       │
├───────────────────────┬─────────────────────────┬───────────────────────────┤
│        METRICS        │     STRUCTURED LOGS     │     DISTRIBUTED TRACES    │
│  Prometheus Gauges,   │  JSON with Contextual   │   OpenTelemetry Spans     │
│  Counters & Histograms│  Correlation Metadata   │   Cross-Service Traces    │
└───────────────────────┴─────────────────────────┴───────────────────────────┘
```

## 2. Distributed Tracing (OpenTelemetry)

Distributed tracing tracks requests across the Next.js frontend, NestJS backend API, PostgreSQL database, BullMQ workers, and external AI providers.

### 2.1 Span Tagging Standards

Every OpenTelemetry span must record these semantic attributes:

- `tenant.id`: Active organization UUID.
- `user.id`: Acting user UUID (or `system_agent` if autonomous).
- `http.route`: Route template (e.g., `/api/v1/bank-statements/:id/reconcile`).
- `workflow.name`: Name of the high-level business saga (e.g., `StatementIngestionPipeline`).
- `agent.name`: Active AI agent identity (e.g., `AccountantAgent`).

## 3. Core System & Business Metrics

Metrics are exported in Prometheus format via `/metrics` (restricted to internal monitoring scrapers).

### 3.1 Business-Critical & Operational Metrics

| Metric Name                                 | Type      | Labels                  | Description / Target                                                            |
| :------------------------------------------ | :-------- | :---------------------- | :------------------------------------------------------------------------------ |
| **`ledger_unbalanced_attempts_total`**      | Counter   | `tenant_id`             | **Target: 0.** Counts any blocked attempt to write an unbalanced journal entry. |
| **`reconciliation_straight_through_ratio`** | Gauge     | `tenant_id`, `bank_id`  | Ratio of transactions reconciled without human touch (Target $> 80\%$).         |
| **`exceptions_pending_count`**              | Gauge     | `tenant_id`, `priority` | Real-time count of unresolved items in the Exception Center.                    |
| **`statement_ingestion_duration_seconds`**  | Histogram | `format`, `status`      | End-to-end time from statement upload to ledger proposal generation.            |
| **`ai_agent_confidence_score`**             | Histogram | `agent_name`, `task`    | Distribution of confidence scores generated by AI classification tools.         |
| **`ai_agent_token_consumption_total`**      | Counter   | `agent_name`, `model`   | Total tokens consumed by agent reasoning and OCR extraction.                    |

### 3.2 Infrastructure & Worker Health Metrics

| Metric Name                     | Type      | Labels                      | Description                                          |
| :------------------------------ | :-------- | :-------------------------- | :--------------------------------------------------- |
| **`http_request_duration_ms`**  | Histogram | `method`, `route`, `status` | API latency distribution ($p50, p95, p99$).          |
| **`queue_jobs_waiting_count`**  | Gauge     | `queue_name`                | Number of pending jobs waiting in BullMQ.            |
| **`queue_job_failed_total`**    | Counter   | `queue_name`, `error_type`  | Unrecoverable worker job failures.                   |
| **`db_connection_pool_active`** | Gauge     | `pool_name`                 | Number of currently utilized PostgreSQL connections. |

## 4. Health Checks & Probes

Health checks are exposed under `/health` and are partitioned into **Liveness** and **Readiness** probes for container orchestrators (Kubernetes / AWS ECS):

1. **Liveness Probe (`GET /health/live`):**
   - Verifies that the Node.js process event loop is responsive.
   - Returns `200 OK` (`{ status: "ok" }`). Does not query external dependencies.
2. **Readiness Probe (`GET /health/ready`):**
   - Verifies connectivity to core dependencies:
     - PostgreSQL: `SELECT 1;` executes within $500\text{ms}$.
     - Redis: `PING` returns `PONG` within $200\text{ms}$.
     - BullMQ: Worker threads are active and polling.
   - If any dependency fails, returns `503 Service Unavailable`.

## 5. Error Tracking (Sentry Integration)

- **Breadcrumbs:** Sentry breadcrumbs automatically capture the last 20 internal log events, DB query templates, and user actions leading up to an unhandled exception.
- **Tenant Tagging:** Every reported error is tagged with `tenant_id` and `user_role` to enable instant filtering by affected organization.
- **PII Stripping:** Sentry SDK hooks must run `beforeSend` to sanitize all request headers, cookies, and local state before transmission.
